# DID Endpoints en iFlex (Fase 1)

**Fecha:** 2026-06-10  
**Entorno:** iFlex / Tractus-X EDC  
**Objetivo:** Documentar funcionalidad, necesidad, utilidad, problema observado y solución de los endpoints DID.

---

## 1. Para que sirven estos endpoints

Los endpoints DID exponen el DID Document de cada participante. Ese documento publica, entre otros datos:

- Identificador DID del participante.
- Claves publicas para verificar firmas.
- Servicios asociados al ecosistema de confianza (por ejemplo CredentialService e IssuerService).

En el flujo IATP/DSP se usan para:

- Resolver identidad del participante remoto.
- Obtener material publico para validacion criptografica.
- Validar VP/JWT y metadatos de confianza en intercambios entre conectores.

Sin resolucion DID correcta, la cadena de confianza se rompe y el intercambio seguro falla.

---

## 2. Configuracion observada en este entorno

Con la evidencia de Fase 1, en este despliegue la publicacion DID activa esta en el wallet stub por BPN:

- Patron valido en este entorno: `https://ssi-dim-wallet-stub.51.178.94.25.nip.io/{BPN}/did.json`

Rutas que no estan publicadas en este despliegue:

- `https://edc-mass-control.51.178.94.25.nip.io/.well-known/did.json` (404)
- `https://edc-ikln-control.51.178.94.25.nip.io/.well-known/did.json` (404)
- `https://ssi-dim-wallet-stub.51.178.94.25.nip.io/{BPN}/.well-known/did.json` (no disponible)

---

## 3. Problema reportado

Se esperaba consultar DID en endpoints de controlplane (o en otra ruta), pero el despliegue actual sirve DID en wallet stub por BPN. Resultado: 404 al consultar rutas no publicadas.

## 5. Por que el navegador dice "No es seguro"

Tu pregunta: "aunque el navegador me indica que no es seguro, por que dice que no es seguro? necesito algun secreto?"

Respuesta:

1. Ese aviso suele ser de confianza TLS/certificado del sitio (CA no confiada localmente, certificado no validado por el navegador, o cadena no completa), no de autenticacion funcional del endpoint DID.
2. No necesitas un secreto para consultar el DID Document, porque es un recurso publico por definicion.
3. `curl -k` funciona porque desactiva validacion estricta de certificado TLS.

Nota operativa:

- Si quieres eliminar el aviso en navegador, hay que resolver confianza de certificados (CA/cadena/SAN), no agregar secretos de aplicacion.

## 6. Solucion para el problema actual

### Solucion directa para este entorno (Fase 1)

- Usar como endpoint de referencia los DID publicados en wallet stub por BPN:
  - `https://ssi-dim-wallet-stub.51.178.94.25.nip.io/BPNL00000000MASS/did.json`
  - `https://ssi-dim-wallet-stub.51.178.94.25.nip.io/BPNL00000002IKLN/did.json`

- No usar, en este despliegue, las rutas `/.well-known/did.json` de `edc-mass-control` o `edc-ikln-control`, ya que actualmente no estan publicadas y devuelven 404.

### Requisito de coherencia

La URL donde realmente se publica el DID debe ser coherente con el DID canonicamente configurado en `iatp.id` y con la estrategia de resolucion del entorno.

### Fase 2 (correccion candidata, no aplicada)

Como posible correccion futura se evaluo cambiar `EDC_IAM_DID_WEB_USE_HTTPS` de `false` a `true` en ambos conectores y en ambos planos (controlplane y dataplane).

Sin embargo, este cambio ya se probo el viernes anterior al 10/06/2026 y produjo una regresion funcional: IKLN dejo de poder acceder al catalogo de MASS. Al volver `EDC_IAM_DID_WEB_USE_HTTPS` a `false`, el acceso al catalogo volvio a funcionar.

Por tanto, a fecha 10/06/2026 esta correccion no se aplica en este entorno y queda abierta una investigacion tecnica detallada para determinar si realmente debe cambiarse ese valor o mantenerse en `false` segun la topologia y el enrutado efectivo.

## 7. Otras configuraciones posibles (referencia)

Aunque en iFlex hoy se observa la publicacion DID en wallet stub por BPN, existen otras configuraciones validas segun arquitectura:

1. DID publicado en wallet stub por participante (actual en este entorno).
2. DID publicado por conector en `/.well-known/did.json` del host del conector.
3. DID publicado externamente en otro host/resolvedor con federacion de confianza.

Cada opcion requiere alinear:

- Valor de `iatp.id`.
- Ruta real publicada del DID document.
- Politica TLS (HTTP/HTTPS) y validacion de certificados.
- Reglas de ingress/routing.

## 9. Fase 3: Catalog request IKLN -> MASS mediante CURL

Para validar el flujo IATP completo desde IKLN contra MASS, se puede ejecutar el catalog request directamente contra el Management API de IKLN.

Comando:

```bash
curl -k -X POST "https://edc-ikln-control.51.178.94.25.nip.io/management/v3/catalog/request" \
  -H "Content-Type: application/json" \
  -H "X-API-KEY: ikln-api-key-change-in-production" \
  -d '{
    "@context": {
      "@vocab": "https://w3id.org/edc/v0.0.1/ns/"
    },
    "counterPartyAddress": "https://edc-mass-control.51.178.94.25.nip.io/api/v1/dsp",
    "counterPartyId": "BPNL00000000MASS",
    "protocol": "dataspace-protocol-http"
  }'
```

Version con salida formateada:

```bash
curl -k -X POST "https://edc-ikln-control.51.178.94.25.nip.io/management/v3/catalog/request" \
  -H "Content-Type: application/json" \
  -H "X-API-KEY: ikln-api-key-change-in-production" \
  -d '{
    "@context": {
      "@vocab": "https://w3id.org/edc/v0.0.1/ns/"
    },
    "counterPartyAddress": "https://edc-mass-control.51.178.94.25.nip.io/api/v1/dsp",
    "counterPartyId": "BPNL00000000MASS",
    "protocol": "dataspace-protocol-http"
  }' | jq .
```

Resultado esperado:

1. Respuesta HTTP 200.
2. JSON de catalogo con datasets/ofertas disponibles.
3. No recibir errores de autenticacion/autorizacion (401/403) ni errores funcionales IATP (por ejemplo 502 por fallo al obtener credenciales).

Si falla:

1. Verificar que `counterPartyAddress` apunta al DSP de MASS y no al Management API.
2. Verificar `X-API-KEY` de IKLN.
3. Correlacionar inmediatamente con logs de `ikln-edc-controlplane`, `dim-wallet-proxy` y `ssi-dim-wallet-stub`.

## 11. Resumen ejecutivo

- El problema observado (404) no implica fallo general del DID, sino consulta a rutas no publicadas en esta topologia.
- La evidencia confirma que los DID de MASS e IKLN estan accesibles en wallet stub por BPN (`/{BPN}/did.json`).
- No se requiere secreto para leer DID documents.
- El aviso de navegador se relaciona con confianza TLS, no con permisos de acceso al DID.
- El cambio `EDC_IAM_DID_WEB_USE_HTTPS=true` queda pendiente de investigacion porque en una prueba previa rompio el acceso de IKLN al catalogo de MASS.
