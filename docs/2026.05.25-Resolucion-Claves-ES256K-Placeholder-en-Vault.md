## 1. Contexto y Síntomas del Problema

### 🔴 Síntoma Principal

Los EDR tokens (Endpoint Data Reference) funcionan correctamente durante los primeros 5 minutos, pero cuando el backend intenta renovarlos automáticamente con `auto_refresh=true`, el DIM Wallet Stub rechaza la operación con el siguiente error:

```
ERROR: Unsupported JWS algorithm RS256, must be ES256K
```

### 📊 Comportamiento Observado en el UI

Al acceder a partner-data, cuando se muestran los Transfer el botón Download no se activa y se queda esperando al token EDR,

### 📊 Comportamiento Observado

| Momento | Acción | Resultado |
|---------|--------|-----------|
| T+0 min | Descarga de datos (token inicial) | ✅ **Funciona** |
| T+5 min | Token expira | - |
| T+6 min | Intento de renovación automática | ❌ **Falla con error RS256/ES256K** |
| T+6 min | Backend devuelve error al frontend | ❌ Descarga falla con HTTP 500 |

### 🎯 Objetivo del Sistema

Permitir que los tokens EDR se renueven automáticamente más allá de los 5 minutos iniciales, cumpliendo con los requisitos del protocolo IATP (Identity And Trust Protocol) de Catena-X/Tractus-X.

## 4. Causa Raíz Identificada

### 🎯 Causa Principal

**Los secrets `tokenSignerPrivateKey` y `tokenSignerPublicKey` en Vault contienen el placeholder `"changeme"` en lugar de claves ES256K (secp256k1) válidas.**

### 🔬 Análisis Técnico

#### ¿Qué es una clave ES256K válida?

ES256K = **Elliptic Curve Digital Signature Algorithm (ECDSA) con curva secp256k1**

**Formato esperado de clave privada:**
```
-----BEGIN EC PRIVATE KEY-----
MHQCAQEEIMGb3xB7dYWqVZ8PqN5hFmJ3cKLwX9T2vR4sQ8nU6pOZoAcGBSuBBAAK
oUQDQgAE8j5wKX9FzN4pY3Rt6LmV8Qw7xH5K2vN3tR9Jc4sW8pL6nT5mQ9zU7vY8
... más líneas base64 ...
-----END EC PRIVATE KEY-----
```

**Formato esperado de clave pública:**
```
-----BEGIN PUBLIC KEY-----
MFYwEAYHKoZIzj0CAQYFK4EEAAoDQgAE8j5wKX9FzN4pY3Rt6LmV8Qw7xH5K2vN3
tR9Jc4sW8pL6nT5mQ9zU7vY8...
-----END PUBLIC KEY-----
```

**Características de secp256k1:**
- Curva elíptica: `secp256k1`
- Tamaño: 256 bits
- Mismo algoritmo usado por: Bitcoin, Ethereum, Catena-X DIDs
- OID ASN.1: `1.3.132.0.10`

#### ¿Por qué el EDC no genera las claves automáticamente?

1. **Seguridad:** Las claves criptográficas deben ser generadas por el administrador, no automáticamente por la aplicación
2. **Persistencia:** Las claves deben sobrevivir reinicios y redepliegues
3. **Control:** El administrador debe tener control sobre el material criptográfico
4. **Backup:** Las claves deben poder respaldarse externamente

### 🔗 Relación con el Error RS256

```
┌─────────────────────────────────────────────────────────────┐
│ EDC intenta usar "changeme" como clave ES256K               │
│   ↓                                                          │
│ No puede realizar operaciones ECDSA con un string           │
│   ↓                                                          │
│ Cae en comportamiento por defecto: RSA (RS256)              │
│   ↓                                                          │
│ DIM Wallet recibe token con algoritmo RS256                 │
│   ↓                                                          │
│ ❌ DIM Wallet RECHAZA: "must be ES256K"                     │
└─────────────────────────────────────────────────────────────┘
```

## 5. Solución Propuesta

### 🎯 Objetivo

Generar y cargar claves ES256K (secp256k1) **criptográficamente válidas** en Vault para reemplazar los placeholders `"changeme"`.

### 🛠️ Herramientas Necesarias

- **OpenSSL** (para generar claves EC)
- **kubectl** (para acceder a Vault)
- **jq** (para validación JSON)

### 📝 Scripts Creados

Se han creado dos scripts automatizados:

#### 1. `fix-es256k-keys-ikln.sh`
- Genera claves ES256K para el conector IKLN
- Ubicación: `/home/xmendialdua/projects/assembly/iflex/fix-es256k-keys-ikln.sh`

#### 2. `fix-es256k-keys-mass.sh`
- Genera claves ES256K para el conector MASS
- Ubicación: `/home/xmendialdua/projects/assembly/iflex/fix-es256k-keys-mass.sh`

### 🔧 Acciones que Realizan los Scripts

Cada script ejecuta los siguientes pasos:

1. **Generación de clave privada ES256K**
   ```bash
   openssl ecparam -name secp256k1 -genkey -noout \
     -out /tmp/[conector]-token-signer-private.pem
   ```

2. **Generación de clave pública correspondiente**
   ```bash
   openssl ec -in /tmp/[conector]-token-signer-private.pem \
     -pubout -out /tmp/[conector]-token-signer-public.pem
   ```

3. **Verificación de la curva**
   ```bash
   openssl ec -in /tmp/[conector]-token-signer-private.pem -text -noout | grep secp256k1
   # Debe mostrar: ASN1 OID: secp256k1
   ```

4. **Backup de claves existentes** (si no son "changeme")
   - Guarda el contenido actual de Vault en `/tmp/[conector]-vault-backup-*.json`

5. **Carga en Vault**
   ```bash
   kubectl exec -n umbrella [conector]-edc-vault-0 -- \
     vault kv put secret/tokenSignerPrivateKey content="[clave PEM]"
   
   kubectl exec -n umbrella [conector]-edc-vault-0 -- \
     vault kv put secret/tokenSignerPublicKey content="[clave PEM]"
   ```

6. **Verificación de integridad**
   - Valida que las claves se guardaron correctamente
   - Verifica que comienzan con `-----BEGIN EC PRIVATE KEY-----`

7. **Reinicio de pods**
   ```bash
   kubectl rollout restart deployment -n umbrella [conector]-edc-controlplane
   kubectl rollout restart deployment -n umbrella [conector]-edc-dataplane
   ```

8. **Espera de rollout completo**
   - Espera hasta 5 minutos a que los pods se reinicien correctamente

### ⚠️ Importante: NO Cambia Configuración

Los scripts **NO modifican** los archivos de configuración de Helm (`values-*.yaml`).

**¿Por qué?** Porque la configuración del EDC ya es correcta:
- Ya apunta a `tokenSignerPrivateKey` y `tokenSignerPublicKey` ✅
- Ya tiene `EDC_DATAPLANE_TOKEN_SIGNING_ALGORITHM: "ES256K"` ✅

**Solo falta:** Reemplazar el contenido de esos secrets en Vault.

## 9. Riesgos y Mitigación

### ⚠️ Riesgos Identificados

#### Riesgo 1: Downtime Durante Rollout
**Probabilidad:** Alta  
**Impacto:** Medio (5-7 minutos sin servicio)

**Mitigación:**
- Ejecutar durante ventana de mantenimiento
- Los pods se reinician secuencialmente (zero-downtime si hay réplicas)
- Las transferencias en curso se interrumpirán temporalmente

#### Riesgo 2: Claves Generadas Incorrectamente
**Probabilidad:** Baja  
**Impacto:** Alto (EDC no arranca)

**Mitigación:**
- Script valida la curva secp256k1 antes de cargar
- Script verifica formato PEM después de cargar
- Si falla, el script se detiene antes del rollout
- Backup automático de claves existentes

#### Riesgo 3: Incompatibilidad con DIM Wallet
**Probabilidad:** Muy Baja  
**Impacto:** Alto (renovación sigue fallando)

**Mitigación:**
- ES256K es el estándar obligatorio de Catena-X
- Ya está documentado que funciona (ver 20260422-resolucion-problema-refresco-token-edr.md)
- Test funcional post-ejecución

#### Riesgo 4: Transferencias Activas Perdidas
**Probabilidad:** Media  
**Impacto:** Bajo (solo reiniciar transferencia)

**Mitigación:**
- Las transferencias completadas conservan sus EDRs en Vault
- Solo las transferencias en curso (STARTED) se interrumpirán
- Los usuarios pueden reiniciar la transferencia desde el dashboard

### 🛡️ Medidas de Seguridad

1. **Backup automático:** Script guarda estado anterior
2. **Validación triple:** Curva + Formato PEM + Lectura desde Vault
3. **Rollback disponible:** Ver sección 10
4. **No destructivo:** Solo modifica contenido de Vault, no configuración

## 12. Conclusiones y Próximos Pasos

### 📌 Resumen Ejecutivo

**Problema:** Claves criptográficas ES256K no configuradas (placeholders "changeme" en Vault)

**Impacto:** Tokens EDR no se pueden renovar después de 5 minutos

**Solución:** Generar claves ES256K reales con OpenSSL y cargarlas en Vault

**Riesgo:** Bajo (configuración ya correcta, solo falta material criptográfico)

**Tiempo:** 10-15 minutos totales (ambos conectores)

**Downtime:** 5-7 minutos por conector (rollout de pods)

### ✅ Criterios de Éxito

La implementación se considerará exitosa cuando:

1. ✅ Vault contiene claves EC válidas (no "changeme")
2. ✅ Pods de EDC están en estado Running
3. ✅ Logs no muestran errores de carga de claves
4. ✅ Test funcional: Token se renueva correctamente después de 5 minutos
5. ✅ NO aparece error "Unsupported JWS algorithm RS256"
