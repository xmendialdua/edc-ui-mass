# Port-Forward Necesario para Partner Login en Desarrollo Local

**Fecha**: 22 de Mayo, 2026  
**Contexto**: Desarrollo local de la aplicación Next.js con autenticación de partners  
**Endpoint afectado**: `http://localhost:3020/partner-login`

---

## ⚠️ IMPORTANTE: ¿Cuándo es necesario el port-forward?

| Escenario | ¿Necesita port-forward? | Motivo |
|-----------|------------------------|--------|
| **Desarrollo en localhost** (`localhost:3020`) | ✅ **SÍ** | La app está fuera del cluster, no puede resolver DNS de Kubernetes |
| **Producción en OVH** (`https://ds-management.51.178.94.25.nip.io`) | ❌ **NO** | Ambos servicios están en el mismo cluster de Kubernetes |

**TL;DR**: Solo necesitas el port-forward cuando desarrollas localmente. En producción (OVH), la aplicación y la base de datos están en el mismo cluster y se comunican directamente.

---

## 🔴 Problema (Solo en Desarrollo Local)

La aplicación corriendo en **localhost:3020** necesita acceder a la **base de datos del Portal de Tractus-X** para autenticar usuarios y obtener información de los partners (IKLN, MASS, etc.).

### Arquitectura del problema:

```
┌─────────────────────────┐
│   Aplicación Local      │
│   localhost:3020        │
│                         │
│   Backend Python        │
│   (FastAPI)             │
└────────┬────────────────┘
         │
         │ ¿Cómo conectar?
         ▼
┌─────────────────────────────────────────────┐
│   Kubernetes Cluster (Umbrella)             │
│   ┌───────────────────────────────────┐    │
│   │  Namespace: portal                │    │
│   │                                   │    │
│   │  Service:                         │    │
│   │  portal-portal-backend-postgresql │    │
│   │  ↓                                │    │
│   │  Pod: PostgreSQL                  │    │
│   │  Puerto: 5432                     │    │
│   └───────────────────────────────────┘    │
└─────────────────────────────────────────────┘
```

### ¿Por qué no funciona directamente?

El hostname configurado en Kubernetes es:

```
portal-portal-backend-postgresql.portal.svc.cluster.local
```

Este hostname **solo es resoluble DENTRO del cluster de Kubernetes**, utilizando el DNS interno de Kubernetes (CoreDNS). Desde tu máquina local (fuera del cluster), este nombre no existe y no puede ser resuelto.

**Errores típicos sin port-forward:**
```
asyncpg.exceptions.InvalidCatalogNameError: Name or service not known
Connection refused
Could not resolve hostname
```

## ✅ Solución: kubectl port-forward

`kubectl port-forward` crea un **túnel local** que redirige el tráfico desde un puerto en tu máquina local hacia un servicio/pod dentro del cluster de Kubernetes.

### Comando necesario:

```bash
export KUBECONFIG=/home/xmendialdua/projects/assembly/tractus-x-umbrella/kubeconfig.yaml

kubectl port-forward -n portal svc/portal-portal-backend-postgresql 5433:5432
```

### ¿Qué hace este comando?

1. **`-n portal`**: Apunta al namespace `portal` donde está el servicio PostgreSQL
2. **`svc/portal-portal-backend-postgresql`**: Nombre del servicio de Kubernetes
3. **`5433:5432`**: Mapeo de puertos:
   - **5433** → Puerto LOCAL en tu máquina (localhost:5433)
   - **5432** → Puerto del servicio PostgreSQL en el cluster

### Flujo con port-forward activo:

```
┌─────────────────────────┐
│   Aplicación Local      │
│   localhost:3020        │
│                         │
│   Conecta a:            │
│   localhost:5433    ◄───┼─── Configurado en .env
└────────┬────────────────┘
         │
         │ TCP Connection
         ▼
┌─────────────────────────┐
│  kubectl port-forward   │
│  (Túnel activo)         │
│  localhost:5433         │
│       ↕                 │
│  K8s Service: 5432      │
└────────┬────────────────┘
         │
         │ Dentro del cluster
         ▼
┌─────────────────────────────────────────────┐
│   Kubernetes Cluster                        │
│   Namespace: portal                         │
│   Service: portal-portal-backend-postgresql │
│   Pod: PostgreSQL                           │
└─────────────────────────────────────────────┘
```

## 📋 Configuración de la Aplicación

### Backend `.env` (Desarrollo Local)

El archivo `src/poc_next/backend/.env` está configurado para usar el port-forward:

```bash
# Portal Database Configuration (for partner authentication)
PORTAL_DB_HOST=localhost        # ← Conecta a localhost, NO al cluster
PORTAL_DB_PORT=5433             # ← Puerto local del port-forward
PORTAL_DB_NAME=postgres
PORTAL_DB_USER=portal
PORTAL_DB_PASSWORD=dbpasswordportal
```

### Código que usa esta configuración

**Archivo**: `src/poc_next/backend/api/routes/partners.py`

```python
PORTAL_DB_CONFIG = {
    "host": os.environ.get("PORTAL_DB_HOST", "localhost"),
    "port": int(os.environ.get("PORTAL_DB_PORT", "5433")),
    "database": os.environ.get("PORTAL_DB_NAME", "postgres"),
    "user": os.environ.get("PORTAL_DB_USER", "portal"),
    "password": os.environ.get("PORTAL_DB_PASSWORD", "dbpasswordportal")
}
```

El endpoint `/api/partners/list` y `/api/partners/login` ejecutan queries contra esta base de datos para:
- Listar todos los partners registrados
- Autenticar usuarios por email
- Obtener información del BPN y conectores de cada partner

## 🔧 Alternativas y Escenarios

### Opción A: Port-forward (Desarrollo - ACTUAL)

✅ **Ventajas:**
- No requiere configuración adicional en el cluster
- Simple y rápido
- Ideal para desarrollo local

❌ **Desventajas:**
- Requiere mantener terminal abierta
- Conexión se pierde si se cierra la terminal o hay problemas de red

### Opción B: NodePort o LoadBalancer

Exponer PostgreSQL externamente (NO recomendado por seguridad):

```bash
kubectl expose service portal-portal-backend-postgresql \
  --type=NodePort \
  --name=postgres-external \
  -n portal
```

❌ **No recomendado**: Expone la base de datos a la red externa

### Opción C: Base de datos local de desarrollo

Usar PostgreSQL local con dump de datos del portal:

```bash
# Instalar PostgreSQL localmente
sudo apt install postgresql-client

# Hacer dump desde el cluster
kubectl exec -n portal portal-portal-backend-postgresql-0 -- \
  pg_dump -U portal postgres > portal_dump.sql

# Restaurar en PostgreSQL local
psql -U postgres -d portal_dev < portal_dump.sql
```

✅ **Ventajas:**
- No depende del cluster
- Más rápido (sin latencia de red)

❌ **Desventajas:**
- Requiere instalación y mantenimiento de PostgreSQL local
- Datos pueden quedar desactualizados

### Opción D: Producción en Kubernetes (OVH) - ⭐ RECOMENDADO

Cuando la aplicación se despliega en Kubernetes (OVH), usa el hostname interno directamente:

**ConfigMap** (`k8s/configmap.yaml`):
```yaml
PORTAL_DB_HOST: portal-portal-backend-postgresql.portal.svc.cluster.local
PORTAL_DB_PORT: "5432"  # Puerto directo, no 5433
```

✅ **Ventajas:**
- **No requiere port-forward** - Ambos pods están en el mismo cluster
- Comunicación directa y rápida entre servicios
- DNS interno de Kubernetes resuelve automáticamente el hostname
- Acceso desde: `https://ds-management.51.178.94.25.nip.io/partner-login`

**Arquitectura en producción:**
```
┌─────────────────────────────────────────────┐
│   Kubernetes Cluster (OVH)                  │
│                                             │
│   ┌───────────────────────────────────┐   │
│   │ Namespace: ds-management-ui       │   │
│   │                                   │   │
│   │  Pod: poc-next-backend            │   │
│   │  Conecta directamente a:          │   │
│   │  portal-postgres.portal.svc...    │   │
│   └─────────────────┬─────────────────┘   │
│                     │                       │
│                     │ DNS interno           │
│                     │ (sin port-forward)    │
│                     ▼                       │
│   ┌───────────────────────────────────┐   │
│   │ Namespace: portal                 │   │
│   │                                   │   │
│   │  Service: portal-postgres         │   │
│   │  Pod: PostgreSQL:5432             │   │
│   └───────────────────────────────────┘   │
│                                             │
└─────────────────────────────────────────────┘
         ▲
         │ HTTPS
         │
    Usuario accede a:
    https://ds-management.51.178.94.25.nip.io/partner-login
```

No requiere port-forward porque ambos pods están en el mismo cluster y comparten la misma red interna.

## 🛠️ Troubleshooting

### Error: "Name or service not known"

**Causa**: Port-forward no está activo

**Solución**:
```bash
# Verificar si está corriendo
ps aux | grep "kubectl port-forward"

# Reiniciar port-forward
kubectl port-forward -n portal svc/portal-portal-backend-postgresql 5433:5432
```

### Error: "Connection refused on port 5433"

**Causa**: Puerto 5433 ya está en uso por otro proceso

**Solución**:
```bash
# Verificar qué proceso usa el puerto
lsof -i :5433

# Opción 1: Matar el proceso
kill <PID>

# Opción 2: Usar otro puerto
kubectl port-forward -n portal svc/portal-portal-backend-postgresql 5434:5432

# Actualizar backend/.env
PORTAL_DB_PORT=5434
```

### Port-forward se desconecta frecuentemente

**Causa**: Timeout de red o problemas de conectividad

**Solución**:
```bash
# Usar script con auto-reconexión
while true; do
  kubectl port-forward -n portal svc/portal-portal-backend-postgresql 5433:5432
  echo "Port-forward disconnected, reconnecting in 5 seconds..."
  sleep 5
done
```

### No puedo acceder al KUBECONFIG

**Causa**: Path incorrecto o permisos

**Solución**:
```bash
# Verificar que el archivo existe
ls -la /home/xmendialdua/projects/assembly/tractus-x-umbrella/kubeconfig.yaml

# Verificar contexto
export KUBECONFIG=/home/xmendialdua/projects/assembly/tractus-x-umbrella/kubeconfig.yaml
kubectl config current-context

# Debe mostrar: kind-umbrella o similar
```

## 🎯 Resumen

### ¿Por qué es necesario el port-forward?
- La base de datos del portal está en Kubernetes, no es accesible desde localhost directamente
- Los hostnames internos de Kubernetes (`.svc.cluster.local`) solo funcionan dentro del cluster
- Tu aplicación en localhost está **fuera** del cluster y no puede resolver esos nombres DNS

### ¿Qué hace el port-forward?
- Crea un túnel desde `localhost:5433` → `portal-postgresql:5432` dentro del cluster
- Permite que tu aplicación local acceda a la base de datos como si estuviera en localhost

### ¿Cuándo NO es necesario?
- ✅ **Cuando la aplicación se despliega en Kubernetes (OVH)** - Ambos servicios en el mismo cluster
  - URL: `https://ds-management.51.178.94.25.nip.io/partner-login`
  - Conexión: Directa usando DNS interno de Kubernetes
  - Configuración: `PORTAL_DB_HOST=portal-portal-backend-postgresql.portal.svc.cluster.local`
  
- ✅ **Si usas una base de datos PostgreSQL local de desarrollo** (alternativa, requiere setup adicional)

### Comparación de Escenarios

| | Localhost | Producción OVH |
|---|---|---|
| **URL** | `http://localhost:3020/partner-login` | `https://ds-management.51.178.94.25.nip.io/partner-login` |
| **Port-forward** | ✅ Necesario | ❌ No necesario |
| **PORTAL_DB_HOST** | `localhost` | `portal-portal-backend-postgresql.portal.svc.cluster.local` |
| **PORTAL_DB_PORT** | `5433` | `5432` |
| **Configuración** | `.env` local | ConfigMap de Kubernetes |
| **Red** | Túnel manual | DNS interno de K8s |
