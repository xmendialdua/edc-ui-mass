## 🔴 Síntoma Observado

Al intentar iniciar una transferencia desde `http://localhost:3020/partner-data` con el botón **"Init Transfer"**, la UI se quedaba bloqueada con el mensaje:

```
Waiting for EDR
EDR token is being generated...
Auto-monitoring active (refresh in ~5s)
```

La transferencia (ej. `87524188-2b96-45c4-b169-2095dc170df7`) nunca avanzaba más allá del estado `REQUESTED` y no se generaba ningún EDR. En los logs del backend se veía:

```
Retrieved 0 EDRs
Transfer IDs in EDR list: []
❌ No EDR found for transfer 87524188-2b96-45c4-b169-2095dc170df7
```

El monitor EDR agotaba los 60 intentos sin éxito.

## 🔬 Diagnóstico

### Paso 1: Logs del control plane de IKLN (consumer)

La transferencia seguía el ciclo esperado en el lado consumer:

```
INITIAL → PROVISIONING → PROVISIONED → REQUESTING → REQUESTED
```

Pero aproximadamente 17 segundos después de alcanzar `REQUESTED`, el provider enviaba un `TransferTerminationMessage`:

```json
{"message": "DSP: Incoming TransferTerminationMessage for process 87524188-..."}
{"message": "TransferProcess 87524188-... is now in state TERMINATING_REQUESTED"}
{"message": "TransferProcess 87524188-... is now in state TERMINATED"}
```

### Paso 2: Logs del control plane de MASS (provider)

El error real estaba en el data plane de MASS al intentar arrancar el flujo de datos:

```json
{
  "level": "ERROR",
  "message": "TransferProcess: ID 6fcf5cb3-... Attempt #1 failed to Start DataFlow. 
  Fatal error occurred. Cause: Transfer request for process 6fcf5cb3-... failed: 
  Remote API returned HTTP 400. [{\"message\":\"Could not generate refresh token: 
  JWSSigner cannot be generated for private key 'tokenSignerPrivateKey': 
  No parser found that can handle that format.\"}]"
}
```

### Paso 3: Inspección del Vault de MASS

```bash
kubectl exec -n umbrella mass-edc-vault-0 -- \
  wget -q --header 'X-Vault-Token: root' \
  'http://localhost:8200/v1/secret/data/tokenSignerPrivateKey' -O - \
  | python3 -c "import sys,json; d=json.load(sys.stdin); 
    print(d['data']['data']['content'][:200])"
```

**Resultado:** `changeme`

Lo mismo para IKLN:

```bash
kubectl exec -n umbrella ikln-edc-vault-0 -- ...
```

**Resultado:** `changeme`

## 🎯 Causa Raíz

Tras un reinicio inesperado del cluster (o de los pods de Vault), el contenido de los Vaults **se perdió** porque Hashicorp Vault en esta instalación usa almacenamiento en memoria (no persistente). Al reiniciarse, los secrets volvieron al estado inicial del Helm chart, que tiene `tokenSignerPrivateKey` y `tokenSignerPublicKey` con el valor placeholder `changeme`.

La variable de entorno del data plane de MASS (y de IKLN) está configurada como:

```
EDC_DATAPLANE_TOKEN_SIGNING_ALGORITHM = ES256K
EDC_TRANSFER_PROXY_TOKEN_SIGNER_PRIVATEKEY_ALIAS = tokenSignerPrivateKey
```

El algoritmo **ES256K** requiere una clave EC en la curva **secp256k1**. Con el valor `changeme`, el parser de claves del EDC no podía ni siquiera interpretar el formato, resultando en el error "No parser found that can handle that format".

> **Este es el mismo problema raíz documentado en**  
> [`2026.05.25-Resolucion-Claves-ES256K-Placeholder-en-Vault.md`](2026.05.25-Resolucion-Claves-ES256K-Placeholder-en-Vault.md)  
> que puede reaparecer después de cualquier reinicio del cluster o de los pods de Vault.

## 🔧 Solución Aplicada

### Scripts ejecutados

Se utilizaron los scripts existentes en `scripts/fix/`:

```bash
export KUBECONFIG=/home/xmendialdua/projects/assembly/tractus-x-umbrella/kubeconfig.yaml

# Fix MASS
cd /home/xmendialdua/projects/assembly/iflex/scripts/fix
bash fix-es256k-keys-mass.sh

# Fix IKLN
bash fix-es256k-keys-ikln.sh
```

### Qué hace cada script

1. **Genera clave privada EC secp256k1** en formato PKCS#8 (requerido por el parser de EDC):
   ```bash
   openssl ecparam -name secp256k1 -genkey -noout -out /tmp/ec-raw.pem
   openssl pkcs8 -topk8 -nocrypt -in /tmp/ec-raw.pem -out /tmp/token-signer-private.pem
   ```

2. **Genera la clave pública** correspondiente:
   ```bash
   openssl pkey -in /tmp/token-signer-private.pem -pubout -out /tmp/token-signer-public.pem
   ```

3. **Verifica** que la curva es secp256k1 antes de continuar.

4. **Copia los ficheros PEM al pod de Vault** y los carga con `vault kv put` (usando saltos de línea reales, no `\n` escapados):
   ```bash
   kubectl cp /tmp/token-signer-private.pem umbrella/mass-edc-vault-0:/tmp/
   kubectl exec -n umbrella mass-edc-vault-0 -- sh -lc \
     'vault kv put secret/tokenSignerPrivateKey content="$(cat /tmp/token-signer-private.pem)"'
   ```

5. **Verifica** que el formato almacenado en Vault es correcto (`-----BEGIN PRIVATE KEY-----`).

6. **Reinicia** control plane y data plane para que carguen las nuevas claves:
   ```bash
   kubectl rollout restart deployment -n umbrella mass-edc-controlplane
   kubectl rollout restart deployment -n umbrella mass-edc-dataplane
   ```

### Estado final de pods tras la corrección


## ✅ Verificación

Tras la corrección, al iniciar una nueva transferencia:

1. El transfer avanza correctamente: `INITIAL → PROVISIONING → PROVISIONED → REQUESTING → REQUESTED → STARTED`
2. El data plane de MASS genera el EDR token con algoritmo ES256K.
3. El EDR aparece en la UI del dashboard.
4. El botón de descarga se activa.
5. El auto-refresh del token (cada ~30 min) también funciona correctamente al usar el algoritmo correcto.

## 🛡️ Prevención Futura

### El problema raíz: Vault no persiste datos tras reinicio

Los pods de Vault (`ikln-edc-vault-0`, `mass-edc-vault-0`) usan almacenamiento en memoria. **Cada vez que se reinician, todos los secrets vuelven al estado inicial del Helm chart** (con valores `changeme`).

### Procedimiento obligatorio tras cualquier reinicio del cluster

Siempre que se reinicien los pods de Vault o el cluster completo, ejecutar:

```bash
export KUBECONFIG=/home/xmendialdua/projects/assembly/tractus-x-umbrella/kubeconfig.yaml
cd /home/xmendialdua/projects/assembly/iflex/scripts/fix

bash fix-es256k-keys-mass.sh
bash fix-es256k-keys-ikln.sh
```

### Síntomas que indican que hay que aplicar el fix

| Síntoma | Causa probable |
|---------|----------------|
| Transfers se quedan en `REQUESTED` y terminan en `TERMINATED` en ~17s | Vault de MASS reiniciado |
| Error en logs MASS: `"No parser found that can handle that format"` | `tokenSignerPrivateKey = changeme` |
| Error en logs MASS: `"Unsupported JWS algorithm RS256, must be ES256K"` | Key cargada en formato RSA en lugar de EC |
| EDR list siempre devuelve 0 resultados para transfers nuevos | Data plane no puede generar tokens |

### Verificación rápida del estado de los Vaults

```bash
export KUBECONFIG=/home/xmendialdua/projects/assembly/tractus-x-umbrella/kubeconfig.yaml

for CONNECTOR in ikln mass; do
  echo "=== $CONNECTOR ==="
  VALUE=$(kubectl exec -n umbrella ${CONNECTOR}-edc-vault-0 -- \
    vault kv get -format=json secret/tokenSignerPrivateKey 2>/dev/null | \
    jq -r '.data.data.content' | head -1)
  if [ "$VALUE" = "changeme" ]; then
    echo "  ❌ tokenSignerPrivateKey = changeme → NECESITA FIX"
  elif echo "$VALUE" | grep -q "BEGIN PRIVATE KEY"; then
    echo "  ✅ tokenSignerPrivateKey = clave EC válida"
  else
    echo "  ⚠️  tokenSignerPrivateKey = formato desconocido: $VALUE"
  fi
done
```
