# 2026-07-08 - Problemas de politicas de publicacion PRTA

## Resumen ejecutivo
Al publicar un asset para el partner PRTA desde data-publication, la publicacion fallaba en la creacion de la Access Policy contra MASS (`POST /management/v3/policydefinitions`) con `HTTP 400 Bad Request`.

Para IKLN no se observaba el problema porque en varios casos la Access Policy ya existia y no era necesario crearla de nuevo.

## Sintoma observado
En la UI aparecia el flujo:

- Contract Policy General ya existe
- Creando Access Policy para PartnerA
- Error con Access Policy (HTTP 400)
- No se pudo asegurar Access Policy
- Publicacion finalizada con errores

El backend mostraba errores repetidos en la llamada a `policydefinitions`.

## Diagnostico realizado
Se realizaron pruebas en tres niveles:

1. Logs de aplicacion backend:
- Confirmaron que el fallo era en la creacion de policy, no en listado de assets/contratos.

2. Pruebas de variantes de payload desde backend:
- Se probaron varias estructuras para constraint/operator de `BusinessPartnerNumber`.
- Todas fallaban con 400 cuando se enviaban junto con metadatos temporales.

3. Prueba directa con curl al endpoint MASS:
- Un payload tipo policy con forma valida de contrato y restriccion por BPN se creaba correctamente.
- El mismo payload, al incluir metadatos temporales en `policy`, devolvia `HTTP 400` HTML generico.

## Causa raiz
El conector MASS rechaza en este endpoint/version los metadatos temporales dentro de `policy`:

- `dct:issued`
- `dct:modified`
- `odrl:validFrom`
- `odrl:validUntil`

La respuesta del conector para este caso era HTML generico de Jetty (`Bad Request`) y no siempre un JSON de validacion detallado.

## Cambios aplicados
### 1) Robustez en create-access-policy
Archivo modificado:
- `src/poc_next/backend/api/routes/phase3.py`

Cambios:
- Se implemento estrategia de intentos por variantes de payload.
- Se dejo como variante principal una forma aceptada por MASS:
  - `action: use`
  - constraints: `Membership`, `FrameworkAgreement`, `UsagePurpose`, `BusinessPartnerNumber`
- Se eliminan metadatos temporales del objeto `policy` para evitar el 400.

### 2) Mejor diagnostico de errores HTTP
Archivo modificado:
- `src/poc_next/backend/clients/edc.py`

Cambios:
- En `create_policy_with_custom_context` se mejoro el error para incluir:
  - status HTTP
  - policy id
  - response body (recortado)
- Esto evita errores opacos y acelera troubleshooting.

## Verificacion
Se verifico con llamada directa al backend:

`POST http://localhost:5001/api/phase3/create-access-policy`

Body:

```json
{
  "bpn": "BPNL00000003PRTA"
}
```

Resultado:
- `success: true`
- Access Policy creada correctamente para PRTA
- Variante aplicada: `C (use + Membership/FrameworkAgreement/UsagePurpose/BPN)`

## Impacto
- Se desbloquea la publicacion para PRTA en el paso de Access Policy.
- Se mejora la observabilidad en errores de policydefinitions.
- Se reduce el riesgo de diagnsticos ambiguos en futuras incidencias.

## Lecciones aprendidas
1. No asumir que todos los conectores aceptan los mismos campos opcionales ODRL/Catena-X en todas las versiones.
2. Mantener payloads minimos y compatibles para endpoints sensibles.
3. Instrumentar errores con status + body para evitar perdida de contexto.

## Estado final
- Incidencia de Access Policy PRTA: resuelta en backend.
- Pendiente operativo recomendado: validar el flujo completo de publicacion desde la UI de data-publication para confirmar extremo a extremo en el entorno actual.
